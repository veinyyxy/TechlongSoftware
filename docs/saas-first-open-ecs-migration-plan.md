# SaaS 租户首次开通改造方案：管理员批准一条实例后，在现有 ECS 集群启动一个临时任务

**状态：2026-11-24（温尼伯）用户确认作为 T1–T3 的开发实施依据，T4 安装及 T5 真实首开分别另审。** 审批、运行配置和已付款任务沿用[执行手册](aws-auto-deployment-execution-runbook.md)的授权边界。文中“现有”指编制方案时核对的仓库代码。

## 1. 改什么，为什么改

客户只和 SaaS 交互：付款后看见待开通，开通后在同一平台取得访问地址。如果开通中断，平台应能指出卡在哪一步，而不需要客户找 GitHub run，也不应让客户再买一次。

现有 Sandbox 路径已能把合格的 Stripe 付款登记为一条待审任务，但实际执行由 [GitHub dispatcher](../.github/workflows/sandbox-first-open-v1.yml) 配对启动 Management、RunOnce 和 Inspect。改造后的系统必须遵守以下边界：

**规则：GitHub 只参与软件交付，不参与任何一笔客户订单的开通。**

- **发布软件时：GitHub Actions 构建 → 推送到 AWS ECR。** 源码保存在 GitHub；发布流程完成 CI、按 Dockerfile 构建镜像，并将镜像推送到项目自己的 AWS ECR 仓库。ECR 存储已构建的镜像，不负责构建。一次发布的版本可以供多笔订单复用。
- **客户开通时：SaaS 批准并调度 → ECS 从 ECR 拉取 → 在 AWS 执行 → 结果回写 SaaS。** ECS 按已选定的镜像摘要（digest）拉取平台开通程序和租户 API 镜像，不从 GitHub 拉源码或镜像，不因新订单重新构建。每单的批准、会话签发、任务编排、核验和回执都不依赖 GitHub Actions、GitHub environment 或 GitHub artifact。软件发布审批不能代替客户开通审批，客户开通也不需要去 GitHub 点批准。

**SaaS 管理后台 → 待开通实例：每条实例记录提供两个按钮。** 付款只登记实例，不启动 ECS。

- **「批准并开通」**：只批准当前实例。服务端先检查该实例是否已经在等待调度或正在开通；如果是，直接显示当前步骤，不再启动。其他未点击的实例保持待开通。
- **「查看开通过程日志」**：只读显示当前实例的开通进度和错误，不会批准、重试或启动任务。未开始时显示「尚无开通日志」；执行中和失败后仍可查看。服务端按管理员的数据权限及实例 ID 限定查询，不能通过更换 ID 查看无权访问的实例。

## 2. 一个开通任务，内部按顺序执行三个步骤

**同一份平台镜像有两个入口：一个运行常驻的 SaaS 网页服务，另一个只处理管理员已批准的单个实例。** 两者在同一个 ECS 集群中运行，但不是同一个容器。

1. **付款时不启动开通容器。** 客户付款成功，平台只登记「待开通」实例；管理员没点批准，这一单就继续等待。
2. **点击批准后才启动。** 管理员在该实例记录上点击「批准并开通」，服务端确认批准成功后，调度器才启动一个临时 ECS 任务：一个容器、一个进程，只处理这一单。重复点击不会再启动一个。
3. **处理结束，退出的是开通容器。** 成功时先记录「已开通」再退出；失败或结果不明时记录最后确认的进度，停止执行，不自动重跑。SaaS 网页保持运行，成功开通的租户 API 也继续提供服务。客户以后访问网页或 API，不会再次触发开通。

以下三个名称只是临时开通进程内部的代码步骤，不是三个任务、三个入口或三个 IAM 身份：

| 顺序 | 内部步骤 | 工作 |
|---|---|---|
| 1 | Worker：领取 | 核对批准、实例归属、首版和执行条件，原子领取这条任务，取得并维护租约。 |
| 2 | Management：开通 | 确认目标库准确且为空，按固定基线初始化、迁移并启用租户数据库登录；准备首代 Secret，通过受控 CloudFormation 入口部署租户 API，等待就绪并下发配置。 |
| 3 | Inspector：技术自检 | 同一进程重新读取数据库、栈、运行镜像、API 就绪和配置，与本单期望值比较。自检通过才原子激活并读回结果；不通过则记录原因，不报成功。 |

三个步骤通过本地函数传参和返回值衔接，使用同一执行编号；阶段进度和已确认的资源引用持久化到 SaaS 控制库。**不启动独立 Inspector 或 Management，不等待跨任务就绪信号、邮箱或第三方签名回执。** 自检仍须读取实际状态，不能把上一步的成功返回当作核验，也不把自检记录标为“独立核验通过”。开通容器退出后，租户 API 继续运行。

## 3. 一单怎样完成

1. **付款 → 登记任务。** 复用验签、订单／会话／金额绑定和去重逻辑。Sandbox 复用既有待审任务；普通购买路径须单独证明“付款已提交但任务交接失败”可按原订单补齐，不能要求再次付款。浏览器回跳不作为付款证明。
2. **点击该行「批准并开通」→ 判断是否已在执行。** 服务端先校验审批权限和实例归属，再在同一数据库事务内按实例判断：已有待调度或执行中的记录，返回其执行编号和当前步骤，不创建新执行；没有活动执行，且订单已付款、实例待开通、任务仍可领取，才记录批准人、时间、目标版本和执行编号，登记启动意图及首条日志。不能靠页面禁用按钮代替服务端判断；两名管理员同时点击也只允许一次启动。
3. **调度 → 启动一个开通任务。** 只处理按钮批准后已提交的启动意图；每个执行编号对应一个稳定的 ECS `clientToken`，一次 `RunTask` 请求的 `count=1`。保存 task ARN 和状态。客户不能指定镜像、命令、角色或网络；Web 重启、多副本或按钮重复提交不能产生第二次开通。
4. **单进程执行：Worker → Management → Inspector。** 按第 2 节的顺序直接调用。每个新副作用前核对租约和资源归属；前一步失败不进入下一步。沿用原属栈管理 AWS 资源，不新增第二套直接创建器。
5. **自检通过 → 原子激活。** 用本次实际观测的结果绑定任务、执行编号和首版；原子写入实例 `active` 和访问地址、部署 `ready`、任务 `succeeded`、首版 `revision=0`。由同一开通任务读回提交结果，并核对客户页面所用状态来源。

### 开通过程日志：只记录定位问题需要的信息

日志写入 **SaaS 控制数据库**，按实例 ID 和本次执行编号关联。管理员打开「查看开通过程日志」时，按时间顺序看到：最后完成了哪一步、现在在哪一步、失败在哪里。复用已有阶段记录，不复制整份容器日志。

| 什么时候记 | 记什么 |
|---|---|
| 批准、启动和关键阶段变化 | 时间、步骤、状态。只记批准、任务启动、建库与初始化、API 部署、自检和激活这些节点的开始、完成或失败；有助于查错时才附 task 或栈的资源标识。 |
| 某一步失败或结果未确认 | 记录具体失败步骤、错误码（如有）、一句去敏原因。无法确认结果时如实写「结果未确认」，不猜成功或失败。异常退出若没来得及写错误，页面显示最后已记录的步骤，不编造原因。 |

例如：「数据库初始化｜完成」之后出现「API 部署｜失败｜AccessDenied｜执行身份无权创建租户栈」，管理员就能判断应查部署权限，不必重新排查付款或建库。**不记录**每次轮询、心跳、完整 SQL、原始请求／响应、密码、令牌、连接串或客户业务数据。查看日志本身不改变执行状态。

### 4.1 按钮点下后，哪些模块要接起来

下面是拟实施的接口和责任边界，不是已上线的实现。接口名称可沿用项目惯例；按编号跟踪的是交付结果，不要求每项新建一个文件或一张表。

| 编号／落点 | 输入 → 处理 → 输出 | 可以查什么来确认已接好 |
|---|---|---|
| M1 管理后台：[实例列表](../app/admin/instances/page.tsx)、[实例详情](../app/admin/instances/[instanceId]/page.tsx) | 每条待开通记录显示「批准并开通」「查看开通过程日志」。前者只提交实例 ID；后者只读取该实例日志。批准成功后显示执行编号、状态、当前步骤。失败后仍能从同一实例查看日志。 | 付款不点按钮时没有执行；执行中再点返回原进度；查看日志没有写入或调度。 |
| M2 服务端批准处理＋控制库 | 从登录会话取得管理员身份，从数据库读取订单、工作区、任务和版本，不信任浏览器传入的付款状态、镜像或权限。按实例串行判断是否已有活动执行。有则返回原编号；无则在同一事务写入批准、启动意图和首条日志。 | 并发批准同一实例只产生一条活动执行；事务中断时不会留下“已批准但找不到执行”的半条记录。 |
| M3 调度器＋ECS 适配 | 读取 M2 已提交的启动意图，以执行编号作为稳定去重依据，向固定任务定义请求一个 task。持久化确认返回的 task ARN；明确被拒时记失败，结果不明时记最后已知状态，不以新编号再启动。 | 用模拟 ECS 检查实际发送的参数、调用次数，以及调度器重启后同一执行能否被找回。 |
| M4 镜像＋开通入口 | 默认命令仍启动 Web。后台入口仅接收执行编号，装载固定配置并核对批准，再按 Worker → Management → Inspector 顺序调用同一进程内的函数。不得依赖本机源码目录、GitHub 凭据或 runner 注入的文件。 | 用同一镜像摘要分别启动两个入口。记录实际加载的迁移程序、基线版本、证书及 `pg_restore` 版本；缺依赖在触碰租户资源前失败。 |
| M5 数据库过程日志＋查询接口 | 复用能表达实例、执行编号、步骤、发生时间和结果的现有记录；不足才补字段。关键阶段结束记结果，失败追加去敏错误码和一句原因。查询按实例授权，再按本次执行编号与事件顺序显示，不混入其他单。 | 注入“建库成功、建栈被拒”故障，从后台能看到最后成功步骤及首个失败步骤；日志不含凭据、SQL 正文或客户数据。 |
| M6 技术自检＋完成回写 | 对比本单期望值与实际数据库身份、栈、ECS 镜像摘要、API 就绪和配置，再原子写入实例、部署、任务及初始版本绑定。提交后读回；管理页面与客户页面使用一致的最终状态。 | 注入错误镜像或健康检查失败，不能显示「已开通」；正常时实例 ID、可访问地址、版本和执行编号均能对应同一单。 |

**后台显示的状态如何判断：** 已付款但未批准显示「待开通」；批准事务已提交但任务还未领取显示「等待调度」；已领取则显示「开通中」及当前步骤；明确失败显示「失败」；外部调用或最终提交结果无法判定显示「结果未确认」及最后已知步骤；仅在 M6 完成并确认后显示「已开通」。这些是页面语义，优先映射已有数据库状态，不要求另造一套状态机。

## 5. 权限和基础设施边界

- **不新增集群、不新增常驻 worker、不改变客户 API 的运行位置。** 每单唯一的临时开通任务运行期间仍产生计算和日志等费用；应有本次任务的结束条件，成功或失败均能退出。任务超时不是自动删库、删客户栈的许可。
- ECS 拉取镜像、输送日志所用的**任务执行角色**，与容器内程序调用 AWS 所用的 **IAM 任务角色**分开。Web 不获得直接建库、建栈或读取租户私密材料的能力；单一后台任务拥有三个步骤所需权限的最小并集，不再声称建库、部署、自检之间有进程级权限隔离。管理会话仅在需要时建立并关闭；不把管理员密码嵌入镜像，也不给 Web 转授这些操作的通用能力。
- **调度权限不能成为间接管理员权限。** 不给 Web 任意 `iam:PassRole`，也不能只限制任务定义却允许通过 ECS overrides 任意换命令、环境或角色。安装前要证明启动入口只接受执行编号和固定启动方式，任务内部再次验证批准与领取；如直接授予 Web 的权限不能保证边界，复用或增加一个只接受固定输入的启动入口，不向公网 Web 开放通用 `RunTask`。
- 沿用原 CloudFormation 归属和现有私有证据位置。核对 ECS 任务到控制库、Express writer、证据存储及 AWS API 的网络路径；**不能因 GitHub runner 原来能连，就假定 ECS 也能连**。本方案不修改数据库版本、节费工具、日常版本发布（D2）或买卖双方业务功能。

### 5.1 安装前逐项对照：谁调用谁、能做什么

| 编号／对象 | 允许的用途 | 明确禁止／核验依据 |
|---|---|---|
| I1 原平台集群、Web 服务、任务定义 | 复用集群、ECR 仓库和 Web 服务。Web 和开通任务均固定到已发布的平台镜像摘要；Web 用原默认命令，临时 task 用固定开通命令。租户 API 使用单独批准的后端镜像摘要。 | 新增的是按单运行的任务定义，不是常驻 Service，也不是新集群。核对模板差异、两个入口、CPU／内存、日志目标、网络及目标摘要；不允许用浮动标签临时替换版本。 |
| I2 Web／受限启动入口 | 验证本条批准；只允许在原集群运行固定任务定义及传递明确列出的角色。若必须用受限启动入口，Web 只交执行编号，由该入口组装固定参数。 | 负向核验：不能任意换命令、镜像、角色、子网，不能直接建库或改租户栈。若无法证明这些限制，不能把通用启动权限直接发给 Web。 |
| I3 ECS 拉镜像身份与开通程序身份 | 拉镜像和写容器日志使用任务执行角色。程序使用另一任务角色及既有受限数据库登录，访问本单的基线、配置、Express 目标及原受控 CFN 路径；只读自检也在该进程内。 | 权限审批列明实际角色、允许动作、资源范围及无法按 ARN 限定的例外。不开通其他租户，不授予任意角色传递，不用管理员密码；不能把进程内函数当作安全边界。 |
| I4 数据路径与存储 | Web 能写批准、读本实例状态和日志；临时任务能到达控制库、Express writer、必要 AWS API、固定证据存储和目标 API。业务操作用验证 TLS 的连接。 | 为每条路径列出来源、目标、用途和复用的网络配置；缺哪条再列哪条差异。不开公网管理端口，不为内部步骤新建 ALB，不把任务日志变成 Secret 存储。 |

**安装审批应能回答四个问题：** 哪些现有资源原样复用；哪个栈具体新增或修改什么；每项权限给谁、用来调用谁；若安装失败，什么已变、什么保持原状。提供实际模板／策略差异和核验方式，不用笼统的“允许 ECS 部署”代替资源清单。本节不是线上读取或写入许可。

## 6. 实施顺序与完成标准

| 阶段 | 唯一交付 | 怎样算通过 |
|---|---|---|
| 1. 离线接入同一镜像 | 保持 Web 默认入口，新增单一开通入口，装配三个顺序步骤及依赖 | 同一镜像能启动 Web 或开通进程；验证三个步骤按顺序且各执行一次，Management 失败不得进入 Inspector，自检失败不得激活；没有 GitHub 环境也能完成离线样例；Web 行为不变；缺批准的样例无法领取或执行。 |
| 2. 离线接通 SaaS 调度 | 两个实例按钮、执行状态检查、单任务 ECS 接口、数据库过程日志 | A、B 已付款，仅批准 A；两人同时点 A 也只启动一次，B 保持待开通，普通客户不能批准。模拟 A 在建库后部署失败：从 A 的日志可见建库完成、部署失败及去敏原因；B 不显示 A 的日志；查看不会重启。另验证重复付款、调度器重启、启动回包丢失或回读失败不导致重复开通或假激活。 |
| 3. 单独审批并安装 AWS 差异 | 复用原集群和镜像仓库，仅准备必要的任务定义、身份、网络和证据授权 | 准确差异、期限、费用和回退点另审；核验 Web 与开通任务的权限边界；不因安装而领取客户任务。 |
| 4. 一次 Sandbox 验收 | 只选一条已付款且仍可领取的任务，走完整 ECS 路径 | 一个开通容器、一次领取；同进程自检确认数据库和 API 就绪；首版绑定及实例激活经提交后读回；客户页面状态一致；临时任务退出；**没有派发任何 GitHub 客户开通工作流**。不重复购买或重做商品、订单测试。 |

**GitHub 独立性验收：** 在上述同一次验收中，所需镜像已按摘要发布到 ECR 后，开通任务在没有 GitHub 凭据、无法访问 GitHub 的条件下也必须走到实例激活和提交后读回。若指定镜像在 ECR 不存在，应报告缺少发布版本并停止，不得转向 GitHub 临时下载、构建或代跑。
